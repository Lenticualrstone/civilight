# 0.2.0 scope (frozen, 2026-11-24)

This file is the frozen scope of app version 0.2.0. Every lane builds what is listed here and nothing else. When this file and a status file disagree, this file wins. When this file and `DECISIONS.md` disagree on how to build (write paths, copy objects, motion), `DECISIONS.md` wins.

**User instruction (2026-11-24):** "이제 지금까지의 기획 사항을 반영하여 0.2.0 버전 앱을 만들어. 검증 시 앱이 크리티컬한 문제를 발생시키는 문제만 생기지 않는다면, 바로 릴리즈 해."

**Version rule (user, 2026-11-24):** `x.y.z`.
- `x = 0` is before the official launch. `x = 1` is the official version.
- `y` goes up for a large feature update. 0.2.0 is one.
- `z` goes up for usability improvements and bug fixes. Anything cosmetic found while verifying 0.2.0 goes to 0.2.1.

**Sources (all planning, read 2026-11-24):**
- `decisions-2026-11-23.md` (planning), including the rows added on 2026-11-24
- `u14-script-chat-input.md` (planning), rows 1–21
- `u15-create-in-place.md` (planning), rows 1–10
- `scope-table-r2.md` (planning), §4 (switch) and §5 (user decisions)
- `next-candidates.md` (planning), section A (U-01 … U-15) and the sketches of the rows the user put in
- `icon-buttons.md` (planning): 89 rows, a 15 · b 33 · c 41. §5.2 (ICON) gives the rule; the file gives each button's class, icon name and accessibility name.
- `docs/release-notes/v0.1.0.md`, `docs/status/qa/0.1.1-backlog.md`

**Precedence, when sources disagree:**
1. A later user decision.
2. Then `decisions-2026-11-23.md` and the U-14 / U-15 files.
3. Then the r2 scope table's recommendations.
4. Then the candidate sketches.

Only what this file names is in. A sketch detail this file does not name is not built, even where no decision replaced it. Examples of decisions that replaced a sketch:
- N-23 choices carry no speaker chip.
- N-13 `그 밖 ▾` has no 레코더 or 갤러리.
- N-41 has no grid view.
- On upgrade, 0.1.0 projects with game data open with the switch **on**, not off as r2 §4-5 first proposed.

**Work already on the branch:** the stopped 0.1.1 run left code on this branch for U-01 … U-11 and U-13, including the U-08 cover and U-09 templates. That code is uncommitted, unbuilt and unverified. Lanes verify and finish it rather than start over.

## 8. Data safety

**Rule 1: simplifying hides; it never deletes.** No 0.2.0 change removes, rewrites or resets stored data. Turning `게임 제작 도구` or any setting off and on again loses nothing.

**Rule 2: the in-place upgrade from 0.1.0 keeps everything.** 0.2.0 installs over 0.1.0 (same signing key) and keeps:
- every project, the example project's state, and the recorder library and audio
- app settings, both trashes with their remaining days, hidden and locked states, gallery images and crops, and backups

Store changes are additive only: new fields with defaults, no field removed or renamed. A 0.1.0 `.civilight` file opens in 0.2.0 unchanged. A downgrade to 0.1.0 is not supported.

## 10. Release gate

0.2.0 is released without asking once verification finds **no critical problem**. Critical means:
- crash or ANR
- data loss (§8 included)
- a hidden-content leak
- a blocked or unresponsive flow
- something that misleads the user

Anything that can hurt usability counts as critical. Cosmetic problems go to the 0.2.1 backlog.

Before release:
1. All unit tests pass, including `CopyLint` and `MotionLint`.
2. Every lane's acceptance checks above are run. A failed check is triaged by the rule above: critical blocks the release, cosmetic goes to the 0.2.1 backlog.
3. Emulator pass at cover and inner width over every module, with motion checked on the emulator.
4. The §8 upgrade check passes.
5. Release notes `docs/release-notes/v0.2.0.md` are written in the style of v0.1.0.
